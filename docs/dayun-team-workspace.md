# Dayun team workspace

The existing staff-only orthomosaic viewer now defaults to a compact workspace. Choose block and gawangan, then **Titik nanas** or **Titik buah**. Population points retain the existing two-second autosave, per-point versions, native-image placement and conflict handling. **Tambah titik nanas** and **Hapus dari hitungan** are primary actions. Fruit mode exposes **Tambah titik buah**, **Hapus titik buah** and **Konfirmasi berbuah**. Adding a fruit point in this explicit staff mode records the staff's visual assessment as confirmed; the automatic shortlist always remains pending until staff acts. Native pixels must be ready before placement. Fruit deletion is a reversible rejection of the fruit annotation only; it never removes or rejects a population point. Repeated fruit placement stays enabled until staff stops adding. Legacy review mode retains its pending-first behavior.

Technical reports, detector metrics, notes, exports and additional review tools are retained in closed details panels. Existing database comparisons and detailed fruit tables remain below the map in a closed details panel. The map header still shows live block/gawangan working counts and save status. Mode and block switches preserve unsaved edits or ask staff to finish saving first; no active user tab is reloaded by deployment.

**Rekap tim A–C** opens the new recap below the map. Each gawangan shows Awal, Tambah, Hapus, Terakhir and Buah tim, with buttons to open the gawangan and an exportable CSV. The three block cards show unique working totals and revision/state. The recap reads the existing staff block-review and fruiting-review endpoints, refreshes every 45 seconds while visible, and accepts current-view editor events immediately. Pending local changes are labelled and protected against late server responses; leaving a saved view retains its newer revision until the next server poll. API failures stay unavailable or explicitly stale instead of becoming zero. Source-run and block identities are checked; fruit labels from another imagery run are not combined.

The shared `dayun-progress-counts.js` helper computes a set comparison of the current detector baseline with effective, non-rejected working points. For each zone, initial points are baseline IDs assigned to that zone, additions are active IDs absent from that initial set, and removals are initial IDs no longer active in that zone. Thus `initial + added - removed = current`. Moved points count as out/in at zone level while leaving the block total unchanged. Same-ID polygon parts are deduplicated. Overlapping zone memberships remain explicit; block totals use unique IDs rather than summing potentially overlapping rows. Historical rejected proposals already removed by filtering are not subtracted again. Deleted manual additions disappear from active additions; this recap is a comparison with the baseline, not a cumulative click-history ledger. The expanded **Arti angka** text explains this without crowding the work panel.

The backend adds read-only source/block metadata and the computed `counts.progress` field to the existing authenticated response. GET never rewrites a correction head. Saves use the same sparse operations, versions and correction prefix. New annotations stay within the existing private fruit history. No census, planting, ethrel, fertilizer, harvest, monitoring, source image, boundary or manifest is changed by this feature. The shared helper contains no private data; Worker and browser use the same arithmetic.
